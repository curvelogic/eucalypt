# Golden diagnostic snapshots

Full-presentation regression snapshots for eucalypt's error diagnostics
(0.14 diagnostics epic **eu-1tkk.7**, task **eu-1tkk.7.4**, design spec
`docs/superpowers/specs/2026-07-21-diagnostics-overhaul-design.md` §5.3).

Every corpus fixture's *entire rendered stderr* is checked in. A change to any
diagnostic anywhere shows up as a reviewable diff.

## The three diagnostics gates, and what each one can tell you

| gate | question it answers |
|---|---|
| `tests/diagnostics_invariants.rs` | Does the diagnostic satisfy five objective invariants (user-file primary, no panic, in-region, user-anchored trace, within trace budget)? |
| `tests/diagnostics_snapshots.rs` (this one) | Did anything about the rendered output change? |
| `tests/harness/errors/*.expect` | Does stderr match a regex, and is the exit code right? |

The snapshots deliberately make **no** claim about quality. They cannot: there
is no validated automatic metric for diagnostic quality, and the design spec's
honesty guardrail forbids inventing one. What they do is force every change in
what a user sees to pass under a reviewer's eye.

## Running

```bash
# Check (this is what CI runs, and what `cargo test` runs)
cargo test --test diagnostics_snapshots

# Regenerate after a deliberate change
cargo xtask diag-snapshot --bless
```

`--bless` regenerates `lib/prelude.blob` and rebuilds before capturing. That is
not incidental: see "Both prelude modes" below.

Review the resulting `git diff` of `tests/diagnostics/snapshots/` and
`tests/diagnostics/DIVERGENCE.md` fixture by fixture. Blessing without reading
the diff defeats the entire mechanism.

## The corpus

| directory | fixtures | why |
|---|---|---|
| `tests/harness/errors/` | 179 | The long-standing error corpus. Its `.expect` sidecars assert regexes; a snapshot of the same fixture is strictly more informative. |
| `tests/diagnostics/corpus/` | 9 | The provocation corpus behind the objective invariant gate. |
| `tests/diagnostics/snapshot-corpus/` | 7 | Many-declaration fixtures — see that directory's `README.md`. |

Fixtures are discovered automatically, so adding one to any of those
directories and running `--bless` is all that is needed. A fixture with no
golden **fails** the gate rather than being skipped.

A handful of fixtures need an extra argument for their diagnostic to be
reachable at all (`-t nonexistent`, `-x xml`); those live in
`tests/diagnostics/snapshot-args.txt`, which also records why `--allow-io` is
deliberately *not* passed.

## Both prelude modes

Each fixture is run twice — under the pre-compiled prelude blob (what a
released binary uses) and under `--source-prelude`. Divergence between the two
has repeatedly hidden real bugs (eu-7x0r, eu-9wq0s), so a snapshot records both
renderings side by side rather than averaging them away:

* modes agree → one `=== both prelude modes ===` section;
* modes disagree → `prelude-modes: divergent` plus two labelled sections, and a
  row in `tests/diagnostics/DIVERGENCE.md`.

`DIVERGENCE.md` is regenerated by `--bless` and asserted by
`divergence_inventory_is_current`, so a newly-introduced divergence is a
one-line change in a single reviewable file rather than something buried in one
of two hundred `.snap` diffs.

Only a binary embedding a *verified* prelude blob can reproduce the blob half,
so `blob_prelude_snapshots_match` and `divergence_inventory_is_current` are
`#[cfg(prelude_blob_ok)]` and run in the `diagnostics-blob-mode` CI job. That
job first asserts the tests are present in the binary's test list — the known
trap is that a `lib/prelude.blob` with a stale mtime does not re-trigger
`build.rs`, leaving `prelude_blob_ok` unset, the tests compiled out, and the
job green having run nothing.

## Normalisation, and prelude-source suppression

A snapshot is only useful if a diff means the *diagnostic* changed.
`normalise` in `tests/diagnostics/snapshot_engine.rs` removes everything else:

| removed | why |
|---|---|
| ANSI colour | terminal-dependent |
| the checkout's absolute path | machine-dependent |
| `[prelude]:LINE:COL` → `[prelude]` | prelude line numbers move on every edit to `lib/prelude.eu`; the combinator *name* is the part that carries meaning and is kept |
| a `lib/*.eu` path → `[prelude]` | a real filesystem path reaching a diagnostic would embed a machine-specific path in a golden |
| prelude **source excerpts** | rustc's `ignore-directory-in-diagnostics-source-blocks` analogue: library source the user did not write and cannot change |
| thread ids in Rust panic banners | differ every run |
| `:LINE:COL` in Rust panic positions | move whenever that `.rs` file is edited; which *file* panicked is kept |

Prelude-source suppression replaces the excerpt with
`<N prelude source line(s) suppressed>` and records `N` as the
`prelude-excerpt-lines` fact — so a regression that starts excerpting library
internals is still visible as a change, while the churny text itself is gone.
(The 0.13.2 baseline excerpted 198 such lines; master excerpts none.)

Every rule is pinned by a self-test in the `normalisation` module of
`tests/diagnostics_snapshots.rs`, including one asserting that **user** source
excerpts survive verbatim — a normaliser that ate those would make the goldens
worthless.

## The `.snap` format

```text
# eucalypt diagnostic snapshot v1
fixture: errors/030_type_mismatch_str
argv: run -L tests/harness/errors --heap-limit-mib 2048 tests/harness/errors/030_type_mismatch_str.eu
prelude-modes: identical

=== both prelude modes ===
exit: 1
errors: 1
warnings: 0
code: EU-EVAL-TYPE
primary: user tests/harness/errors/030_type_mismatch_str.eu:2:6
help-lines: 0
note-lines: 2
secondary-labels: 0
trace-frames: 1
trace-user-frames: 1
trace-prelude-frames: 0
prelude-excerpt-lines: 0
rust-panic: no
--- stderr ---
error[EU-EVAL-TYPE]: type mismatch: expected number, found string "hello"
  ...
```

The facts block is derived from the **human** rendering, not from
`--error-format json`. That is what makes a retroactive baseline capture
possible: an `eu` binary from before the structured diagnostic model existed
(eu-1tkk.7.1) still produces human output the same extractor can read.

## Baselines and release evidence

`docs/superpowers/diagnostics-baselines/` holds frozen captures at specific
refs, stored as single-file bundles so that comparing two points in history is
one readable `diff`. See that directory's `README.md`.

```bash
# Capture with any binary, including one built from a release tag
cargo xtask diag-snapshot --capture --from-ref 0.13.2 --out /tmp/0.13.2.txt

# Tabulate two captures into a before/after report
cargo xtask diag-snapshot --compare /tmp/0.13.2.txt tests/diagnostics/snapshots \
    --mode source --out /tmp/report.md
```

Debug and release builds produce byte-identical diagnostics (verified for all
195 fixtures), so a release-built baseline is comparable with the debug-built
goldens `cargo test` produces.
