# eu-oaz72.37 — `eu run --profile`: overhead and the 2025 day09 part 2 hotspot

Date: 2026-11-14. Bead: eu-oaz72.37. Every figure is **measured-single**
(one session, one cloud container, release builds from clean).

## What was built

`eu run --profile` charges each machine tick, closure allocation and heap
byte to the source location executing at the time (the machine's
scope-accurate annotation register, with fallbacks to the current closure's
and its environment's annotation), and prints a top-N table to stderr.
`--profile-folded FILE` also writes folded stacks sampled every 1009 ticks
(innermost 64 frames). User guide: `docs/reference/cli.md` ("Profiling").

Engine hooks, all in `src/eval/bytecode/machine.rs`: the three dispatch
loops (`run`, `drive_whnf`, `drive_to_whnf`) are generic over a
`const PROFILE: bool`, and the instantiation is chosen once per loop entry.
The `PROFILE = false` loops are the previous loops. A per-tick `profile_tick`
call appears only in the `true` instantiation. The heap gained one
`Cell<u64>` byte counter, incremented on every allocation
(`src/eval/memory/heap.rs`); this is the only change on the unprofiled path.

## The 2025 day09 part 2 hotspot

The real puzzle input is not in the repository. The figures below come from
a synthetic 496-vertex rectilinear polygon of the same size (248 points on a
jittered circle, x then y steps), run with
`eu --source-prelude run --profile --profile-folded … run/day09.eu -t part-2`.
It completes in about 4 s and 44.1 M ticks, because a convex polygon prunes
well. The mechanism generalises, but the magnitudes on the real input do not.

Self cost (top rows of the table):

| ticks | % | location |
|---|---|---|
| 9.95 M | 22.5% | `foldr (prelude)`, `filter`'s traversal |
| 5.08 M | 11.5% | `filter (prelude)` |
| 4.56 M | 10.3% | `inner-step at day09.eu:152:3` |
| 3.01 M | 6.8% | `v-spans? at day09.eu:63:3` |
| 4.04 M | 9.2% | `at-y?` (two sites, day09.eu:69) |

Folded stacks (43,730 samples) split the run three ways:

- **29% is level construction, forced lazily inside the search.**
  `xsect` filters all 496 edges (`v-spans?`, `has-y?`) and `tile-xs-at`
  filters all 496 points (`at-y?`), once per level: O(levels × points). No
  separate phase builds the levels. They are thunks, and whatever touches a
  level first pays for it: `maxw` in 61% of those samples (forced by the
  `max-possible` test of the first `outer-step`), `row-width` (the `rm`
  seed) in 37%.
- **23% is `max-rect`'s own work**, mostly `clamp-to`'s `filter` and
  `cross`.
- **48% is the fold and pruning machinery.** 45% of all samples sit under
  three or more nested `inner-step` frames. The inner `foldl` builds
  its `[left, right, best]` accumulator lazily, and `pruned?` reads the
  previous step's `best`, so forcing the final `!! 2` unwinds the whole
  chain recursively. This is the lazy-accumulator pattern of eu-oaz72.27
  (`foldl-strict`).

This explains the per-step anomaly the bead records: 20–65 k ticks per inner
step, and `max-rect` at 36 k ticks in situ against 1.5 k in isolation. A
step's tick count includes every thunk it is the first to force: the
lazily built levels, the tile lists, and earlier steps' unforced
accumulators. Timed in isolation, those inputs are already values. The step
itself is cheap. Its inclusive cost is the cost of the data it first
touches.

Source-level fixes suggested by the profile (not applied here): build the
levels strictly, with a single sweep that sorts edges by y rather than a
filter over all edges per level; and keep the inner accumulator strict
(eu-oaz72.27).

## Limits

- On the blob path, code inside the pre-compiled prelude has no source
  information, so its internals land in one `<prelude internal>` row (41%
  of a small map/filter/foldl program). `--source-prelude` names them, but
  it compiles differently: 3.79 M against 4.14 M ticks for the same
  program. Carrying prelude source information in the blob would close this
  gap, but it is a wire-format change and needs a separate decision.
- The figures are self cost. Inclusive cost comes only from the sampled
  folded stacks, which keep the innermost 64 frames, so outer frames on
  deep stacks are under-counted.
- Attribution is at instruction granularity. An op that changes the
  annotation (closure entry, return) is charged to its new location.
