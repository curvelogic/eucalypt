- **Date:** 2026-11-13
- **Bead:** eu-oaz72.4 (P0) — GC collects only once the heap limit is reached
- **Commit measured:** master `1d1de2e` (after #1142 volume trigger, #1149,

Wall figures measured-verified; set-churn wall is near the 1 s mark, so its
ratio is indicative. The bead's earlier set-churn figure under a 512 MiB cap
(328 s thrashing, 952 MB RSS) is now 1.3 s (measured-single), with no
thrashing.

**The set footprint is not bounded.** Peak blocks scale with n
(deterministic): 3,757 / 7,842 / 17,066 / 34,345 at n = 4k / 8k / 16k / 32k,
with Blocks Recycled 0. Under `--heap-limit-mib 256`, n = 32000 ends at
34,638 blocks (~1.08 GB, four times the cap) and succeeds; under 512 MiB,
n = 16000 peaks at 17,066 blocks (533 MB). The collector's measured live
volume after each collection stays at 8..2,051 blocks (temporary
instrumentation, not committed), so the live-based limit check never fires.

Cause (eu-oaz72.73): `HeapState::replace_overflow` always takes a fresh
block, so medium objects (> one line, < one block — set and vec storage)
never reuse swept blocks; only head replacement consumes them. A throwaway
patch reusing fully free recycled blocks for overflow cut the n = 32000
peak to 11,779 blocks (projected as the direction of a fix, not a fix). The
remainder is live data on a 128,010-deep stack (max stack 4n): this fold's
accumulator is not strict, noted on eu-oaz72.73 for triage.

Vec churn at n = 4000 under a 256 MiB cap peaked at 5,153 blocks
(deterministic); its many small allocations consume recycled blocks
through head replacement, which hides the defect.

## 3. Heap-limit exhaustion

`tests/fixtures/heap_limit_exhaustion.eu` (2M-element reversed list held
live) and a 20M-element variant, measured-single:

| Cap | Exit | Time | Message |
|---|---|---|---|
| 32 MiB | 1 | 0.7 s | 29 MiB live against 32 MiB |
| 256 MiB | 1 | 5.0 s | 225 MiB live against 256 MiB |
| 1024 MiB (20M) | 1 | 23.6 s | 903 MiB live against 1024 MiB |

The error fires when live data fills the cap. It does not fire when the
footprint exceeds the cap through unreclaimed blocks (§2). Under the 32 GiB
default on a machine with less RAM, live-data growth still meets the kernel
first: the default is an engine default and the owner's decision (bead
description).

### 2. Cap behaviour — forced form, and the non-strict form located

Forced set churn under `--heap-limit-mib 256` and `64`: completes (exit 0),
RSS 64 MB, at n = 4k and 32k — footprint (32 MiB) is well under both caps.
**Pass.**

Non-strict `foldl` form, to locate the overshoot. The program, with n
substituted:

```eu
base: range(0, 1000) set.from-list
step(s, i): s set.remove(i % 1000) set.add(i % 1000)
r: foldl(step, base, range(0, 32000)) set.size
```

Deterministic `-S`: at
cap 256, n = 32,000, Peak Blocks **7,873 (~246 MiB, under the 256 cap)**, Max
Stack 128,010, completes. The heap footprint stays within the cap; the RSS it
reaches (419 MB, measured-single) is the 128,010-deep continuation stack
(non-heap, Rust-side) that the non-strict accumulator builds — eu-oaz72.27
territory, not GC footprint. (Unbounded, the same program peaks at 11,778
blocks.) #1171's report gives 7,728 blocks and Max Stack 129,012 for a
repro it describes but does not quote; a reviewer's reconstruction gave
7,722 / 129,014 and the same cap-64 error to the MiB. The figures here
are for the program above only. At cap 64 the 246 MiB of live heap data cannot
fit, so a eucalypt error is raised, not a kernel OOM:
`heap limit exceeded: 57 MiB remains in use after garbage collection, against
a heap limit of 64 MiB`. So the GC-governed footprint either fits-and-
completes or raises `HeapLimitExceeded`; it never grows past the cap without
one. **Pass.**
