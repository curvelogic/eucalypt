# eu-oaz72.4 acceptance: volume-based GC trigger

- **Date:** 2026-11-13
- **Bead:** eu-oaz72.4 (P0) — GC collects only once the heap limit is reached
- **Commit measured:** master `1d1de2e` (after #1142 volume trigger, #1149,
  #1154 large objects freed, #1157 emergency sweep fix, eu-oaz72.34
  constant-stack loops, #1158 strict accumulation)
- **Build:** `cargo clean && cargo build --release`; prelude blob as built
  (`prelude_config: blob`)
- **Host:** Linux 6.18 x86_64 container, 4 vCPU, 15 GiB RAM; rustc 1.99.1;
  load average 1.0–1.6 during runs (no other builds or benchmarks)
- **Method:** `docs/superpowers/engine-ab/PROTOCOL.md` adapted to a
  configuration A/B on one binary: three heap configurations (default
  32 GiB, `--heap-limit-mib 0`, `--heap-limit-mib 1024`) interleaved run for
  run, N = 7, median wall with min..max; a separate `-S` pass per
  configuration for ticks, collections and peak blocks; peak RSS from
  `wait4` rusage; every `eu` under `timeout`; `EU_PP_THRESHOLD=999999999`
  (sequential). Two sessions (s1, s2) for measured-verified.

| Criterion | Bead repro (1e6 loop) | Medium-object churn (set) |

eu-oaz72.4's own defect — the trigger — is fixed. The bead stays open
because the coordinator's note asks for set/vec churn in its acceptance,
and set churn exposes a separate allocator defect, eu-oaz72.55 (P0), on
which eu-oaz72.4 now depends.

Deterministic (`-S`, identical in every configuration; measured-verified):
49,000,208 ticks, 10,000,035 allocs, 53 collections, peak 1,026 blocks
(32 MiB), max stack 7. Before #1142: 0 collections and 54,727 blocks
unbounded; 39,326 collections under a 1024 MiB cap.

Peak blocks do not grow with n (measured-verified): 1,026 at n = 250k, 1M
and 4M (13, 53, 214 collections).

## 2. Churn repros

| Repro | Config | s1 wall | s2 wall | RSS | collections / peak blocks |
|---|---|---|---|---|---|
| set | default | 1.066 (0.962..1.300) | 1.133 (1.029..1.444) | 728 MB | 11 / 17,066 |
| set | unbounded | 1.078 (1.036..1.200) | 1.087 (0.973..1.388) | 728 MB | 11 / 17,066 |
| set | cap 1024 | 1.060 (0.964..1.195) | 1.068 (0.989..1.419) | 728 MB | 11 / 17,066 |
| vec | default | 4.423 (4.110..5.120) | 4.302 (4.160..4.507) | 110 MB | 85 / 2,056 |
| vec | unbounded | 4.468 (4.337..4.721) | 4.361 (4.279..4.580) | 110 MB | 85 / 2,056 |
| vec | cap 1024 | 4.305 (4.114..4.996) | 4.275 (4.143..4.484) | 110 MB | 85 / 2,056 |

Wall figures measured-verified; set-churn wall is near the 1 s mark, so its
ratio is indicative. The bead's earlier set-churn figure under a 512 MiB cap
(328 s thrashing, 952 MB RSS) is now 1.3 s (measured-single), with no
thrashing.

**The set footprint is not bounded.** Peak blocks scale with n
(deterministic): 3,757 / 7,842 / 17,066 / 34,345 at n = 4k / 8k / 16k / 32k,
with Blocks Recycled 0. Under `--heap-limit-mib 256`, n = 32000 ends at
34,638 blocks (~1.08 GB, four times the cap) and succeeds; under 512 MiB,
n = 16000 peaks at 17,066 blocks (533 MB). The collector's measured live
volume after each collection stays at 8..2,051 blocks (temporary
instrumentation, not committed), so the live-based limit check never fires.

Cause (eu-oaz72.55): `HeapState::replace_overflow` always takes a fresh
block, so medium objects (> one line, < one block — set and vec storage)
never reuse swept blocks; only head replacement consumes them. A throwaway
patch reusing fully free recycled blocks for overflow cut the n = 32000
peak to 11,779 blocks (projected as the direction of a fix, not a fix). The
remainder is live data on a 128,010-deep stack (max stack 4n): this fold's
accumulator is not strict, noted on eu-oaz72.55 for triage.

Vec churn at n = 4000 under a 256 MiB cap peaked at 5,153 blocks
(deterministic); its many small allocations consume recycled blocks
through head replacement, which hides the defect.

## 3. Heap-limit exhaustion

`tests/fixtures/heap_limit_exhaustion.eu` (2M-element reversed list held
live) and a 20M-element variant, measured-single:

| Cap | Exit | Time | Message |
|---|---|---|---|
| 32 MiB | 1 | 0.7 s | 29 MiB live against 32 MiB |
| 256 MiB | 1 | 5.0 s | 225 MiB live against 256 MiB |
| 1024 MiB (20M) | 1 | 23.6 s | 903 MiB live against 1024 MiB |

The error fires when live data fills the cap. It does not fire when the
footprint exceeds the cap through unreclaimed blocks (§2). Under the 32 GiB
default on a machine with less RAM, live-data growth still meets the kernel
first: the default is an engine default and the owner's decision (bead
description).
